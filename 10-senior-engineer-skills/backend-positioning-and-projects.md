# Backend Positioning And Portfolio Projects

## Positioning

Do not present yourself as:

```text
Node.js / Golang / React engineer
```

That sounds like three equal identities and can invite deeper React questioning.

Present yourself as:

```text
Backend Engineer: Go + Node.js
with full-stack exposure using React
```

Strongest identity:

```text
Backend / Infrastructure Engineer
Go • Node.js • REST APIs • SQL/MongoDB • Kafka • Redis • Cloud
```

React positioning:

```text
Comfortable building frontend dashboards/internal tools using React.
```

Do not present React as expert-level unless the role requires it and you are ready for deep React questions.

## Why This Helps

Many service companies and startups value engineers who can handle:

- backend APIs
- database work
- basic frontend integration
- deployment
- debugging
- client/project work

If you build 2-3 complete projects from scratch, you can honestly say:

```text
I have hands-on project experience building full-stack applications using Node.js, Go, SQL, and React.
```

This is not fake professional experience. It is real hands-on project experience.

## Professional-Style Project Rule

Build projects like real work:

- requirements
- API design
- database schema
- backend implementation
- frontend dashboard
- auth
- validation
- logging
- Docker
- deployment
- README
- GitHub commits
- issue tracker
- basic tests

Avoid toy projects:

- todo app
- weather app
- calculator
- basic blog only

Build backend-heavy internal tools because that matches your resume and interview target.

## AI Usage Rule For Portfolio Projects

Correct rule:

```text
You write the code.
AI explains, reviews, gives hints, and helps debug.
```

Use AI like a mentor, not like a contractor.

Do not do this:

- ask AI to build the full auth system
- ask AI to generate the entire backend
- copy-paste full components or APIs
- let AI design everything without understanding
- move fast but learn nothing

Use AI for:

- project requirements
- database schema review
- API design feedback
- debugging hints
- explaining docs
- code review
- test case ideas
- README structure

Good prompt:

```text
I am building this feature myself. Do not give me full code. Explain the approach, list the steps, and give hints if I get stuck.
```

Best workflow per feature:

1. Read docs lightly.
2. Design the API/schema.
3. Write code yourself.
4. Run it.
5. If stuck, ask AI for hint/debug.
6. Fix it yourself.
7. Write notes: what I learned.
8. Commit to GitHub.

Allowed small snippets:

- syntax examples
- tiny middleware example
- SQL query example
- error pattern example

Avoid full project files unless you are using them only as reference and rewriting the implementation yourself.

Interview reason:

```text
I built this project from scratch. I designed the schema, wrote the APIs, handled auth, connected frontend, added Docker, and debugged issues myself.
```

That line only feels real if your hands did the work.

Project commandment:

```text
AI can guide me.
AI cannot replace my hands.
```

## Project Phase Starting Rule

```text
Build projects yourself.
Use AI as mentor/reviewer/debugger only.
No direct copy-paste full code.
```

Start with:

```text
Job Application Tracker
Node.js + PostgreSQL + React + Docker
```

Why this is first:

- repairs Node.js confidence
- repairs SQL confidence
- strengthens REST API practice
- gives React/full-stack exposure without pretending to be a React expert
- adds auth practice
- adds Docker practice
- is directly useful for the job search

Timing:

```text
Today's priority remains SQL repair + DSA recall + hydration reset.
Project phase starts after today's repair block or from tomorrow with a clean board.
```

## Project 1 - Job Application Tracker

This is useful for your real life and believable in interviews.

Stack:

```text
Frontend: React + TypeScript
Backend: Node.js + Express/NestJS
Database: PostgreSQL
Cache optional: Redis
Auth: JWT
Deployment: Docker
```

Features:

- user login
- add job applications
- track company, role, status, salary, source, recruiter
- add interview rounds
- add notes and feedback
- dashboard totals
- active pipelines
- rejected count
- interviews scheduled
- follow-up reminders
- search/filter by status/company/date

Backend skills covered:

- Node.js
- REST APIs
- SQL
- joins
- pagination
- authentication
- authorization
- validation
- error handling
- Docker

Resume bullet later:

```text
Built a full-stack job application tracker using Node.js, React, PostgreSQL, JWT auth, and Docker, with dashboards, filtering, interview-stage tracking, and follow-up reminders.
```

## Project 3 - Event Ingestion Pipeline

This covers Kafka, ClickHouse, Go, Node, and production-style backend.

Stack:

```text
Producer API: Node.js or Go
Queue: Kafka or Redpanda
Consumer: Go
Storage: ClickHouse
Dashboard: React
Cache optional: Redis
Docker Compose
```

Features:

- API receives events
- events published to Kafka
- Go consumer reads events
- consumer validates and writes to ClickHouse
- dashboard shows event counts
- retry failed events
- DLQ table/topic
- basic consumer lag monitoring

Backend skills covered:

- Kafka
- Go workers
- ClickHouse
- event-driven architecture
- data pipelines
- retry
- DLQ
- idempotency
- observability
- Docker Compose

Resume bullet later:

```text
Built an event ingestion pipeline using Kafka, Go consumers, ClickHouse, and React dashboard, with retry handling, DLQ flow, and basic monitoring for ingestion health.
```

## Interview Positioning Line

Use this:

```text
My strongest profile is backend engineering with Go and Node.js. I also have full-stack exposure and can build React dashboards/internal tools when needed, but my core strength is backend APIs, databases, distributed systems, and production debugging.
```

## Main Rule

```text
Backend identity first.
Full-stack exposure second.
React expert never unless deeply prepared.
```
